# فصل ۱۰ — تست

## ۱. هرم تست این پروژه

```
                 ┌──────────────────────┐
                 │  E2E (Playwright) 15 │  مرورگر واقعی، سرور واقعی
               ┌─┴──────────────────────┴─┐
               │ کامپوننت (RTL + jsdom) 26 │  React + SDK واقعی + شبکه‌ی جعلی
             ┌─┴──────────────────────────┴─┐
             │ SDK (Vitest) 25              │  بدون DOM
           ┌─┴──────────────────────────────┴─┐
           │ بک‌اند (pytest) ~140              │  دیتابیس واقعی (SQLite/Postgres)
           └──────────────────────────────────┘
```

هر لایه چیزی را می‌گیرد که بقیه نمی‌گیرند. در این پروژه:

| باگ | کدام لایه پیدایش کرد |
| --- | --- |
| کرسر با `+` خراب | تست API بک‌اند |
| `dispose` یک به‌روزرسانی آخر می‌فرستاد | تست SDK |
| فوکوس بعد از Reply | تست کامپوننت |
| client مرده در StrictMode | **فقط E2E** |
| حذف همه‌ی paddingها | **فقط اسکرین‌شات** |
| فونت میزبان داخل ویجت | **فقط اسکرین‌شات + E2E تقویت‌شده** |
| دور زدن rate limit | تست امنیتی هدفمند |

**درس:** پوشش کد بالا با تست واحد، باگ‌های یکپارچه‌سازی و بصری را نمی‌گیرد. حتماً به اسکرین‌شات‌هایتان **نگاه کنید**.

## ۲. Fake در برابر Mock

تست‌های SDK و React از **fake** استفاده می‌کنند، نه mock:

- `FakeWebSocket` (`packages/chat-client/test/fakes.ts`): یک پیاده‌سازی واقعی ولی کنترل‌شدنی از WebSocket، با متدهای سمت سرور (`ready()`، `emit()`، `serverClose(code)`).
- `fakeFetch(routes)`: یک جدول مسیر که پاسخ‌های واقعی `Response` برمی‌گرداند.

تفاوت این است که mock بررسی می‌کند «این تابع با این آرگومان صدا زده شد؟»، که تست را به جزئیات پیاده‌سازی گره می‌زند. fake یک **رفتار** شبیه‌سازی می‌کند، و تست نتیجه را بررسی می‌کند («پیام در لیست با وضعیت sent است»). تست‌های React از **ChatClient واقعی** روی این fakeها استفاده می‌کنند، پس منطق SDK هم همزمان تست می‌شود.

## ۳. تست‌های بک‌اند

- **کاربر استاندارد Django:** `tests/settings.py` از `auth.User` استفاده می‌کند. این ثابت می‌کند پکیج به مدل کاربر خاصی وابسته نیست.
- **`on_commit`:** فصل ۳ را ببینید (`django_capture_on_commit_callbacks` یا `transaction=True`).
- **WebSocket:** `WebsocketCommunicator` از Channels. تله: `receive_json_from(timeout=…)` وقتی timeout شود، **کل consumer را cancel می‌کند** (رفتار asgiref) و تست‌های بعدی با خطای عجیب `CancelledError` شکست می‌خورند. برای بررسی «هیچ پیامی نیامد» از `receive_nothing()` استفاده شده (helper `none_of`).
- **ورودی‌های بدشکل:** با `pytest.mark.parametrize` لیستی از ورودی‌های خراب تست می‌شود (`test_malformed_user_ids_are_rejected_not_500`).

## ۴. تست همزمانی واقعی

SQLite همه‌ی نوشتن‌ها را سریالی می‌کند، پس تست همزمانی روی آن معنایی ندارد. PostgreSQL لازم است. روی سروری بدون Docker و sudo، پکیج `pgserver` یک PostgreSQL واقعی در فضای کاربر اجرا می‌کند:

```python
import pgserver
srv = pgserver.get_server("/tmp/pgdata")
print(srv.get_uri())   # postgresql://postgres:@/postgres?host=/…socket
```

```bash
TEST_DATABASE_URL="<uri>" pytest
```

`tests/test_concurrency.py` با `threading.Barrier` همه‌ی threadها را در یک لحظه رها می‌کند (تا واقعاً همزمان باشند)، هر thread اتصال دیتابیس خودش را دارد و در پایان `connection.close()` می‌کند. چیزهایی که بررسی می‌شوند:

- ۸ درخواست همزمان ساخت گفتگوی خصوصی، از هر دو طرف → دقیقاً یک گفتگو.
- ۶ فرستنده × ۱۰ پیام + تکرار هر پیام → `seq`های ۱ تا ۶۰ بدون فاصله و بدون تکرار.
- افزودن همزمان یک عضو توسط دو ادمین → یک ردیف عضویت.

برای اینکه نتیجه‌ی تصادفی نباشد، این تست‌ها چند بار پشت‌سرهم اجرا شدند.

## ۵. Playwright (E2E)

- **دو مرورگر = دو کاربر:** `userPage(browser, 'alice')` یک context جدا (کوکی جدا) می‌سازد. تست تحویل بلادرنگ واقعاً با دو session کار می‌کند.
- **آفلاین واقعی:** `context.setOffline(true)` → بنر آفلاین → کاربر دیگر پیام می‌فرستد → `setOffline(false)` → پیام جاافتاده ظاهر می‌شود.
- **میکروفون مصنوعی:** flagهای Chromium در `playwright.config.ts`.
- **Locatorهای دسترس‌پذیر:** `getByRole('button', { name: 'Send voice message' })`.

### تست‌های flaky و ریشه‌یابی‌شان

| علامت | علت واقعی | راه‌حل |
| --- | --- | --- |
| تعداد استیکرها «۵ به‌جای ۱» | شمارش «قبل» زمانی گرفته شد که تاریخچه هنوز لود نشده بود | helper `openConversation` تا لود شدن تاریخچه صبر می‌کند (`aria-busy=false`) |
| تست «Enter ارسال می‌کند» ۱ بار از ۵ | timeout ack در helper تست فقط ۵۰ms بود | ۲۰۰۰ms |
| `hasText: 'Ship it 🚀'` پیدا نمی‌شود | ایموجی حالا `<img alt>` است و `hasText` متن alt را نمی‌خواند | جستجو با `getByRole('img', { name: '🚀' })` |

**درس:** تست flaky را با `retry` پنهان نکنید. ریشه‌اش تقریباً همیشه یک فرض اشتباه درباره‌ی **زمان** یا **وضعیت** است.

## ۶. اسکرین‌شات‌ها به‌عنوان تست بصری

`e2e/screenshots.spec.ts` اسکرین‌شات‌های README را از اپ واقعی می‌سازد. چند باگ بصری فقط این‌طور پیدا شدند (فصل ۸). یک قدم بعدی خوب این است که این‌ها با یک تصویر مرجع مقایسه شوند (`toHaveScreenshot`) تا تغییر ناخواسته‌ی ظاهر در CI شکست بخورد.

## ۷. تست پکیج‌ها از دید مصرف‌کننده

`scripts/verify-packages.sh`:

1. wheel پایتون را build می‌کند، در یک venv **تمیز** نصب می‌کند و تست‌های `examples/django-integration` را روی آن اجرا می‌کند.
2. پکیج‌های npm را با `npm pack` به tarball تبدیل می‌کند، در یک پروژه‌ی خالی **بیرون** از workspace نصب می‌کند، با `skipLibCheck: false` typecheck می‌کند و در Node خام import می‌کند.

این کار باگ‌هایی را می‌گیرد که در monorepo دیده نمی‌شوند: فایلی که در `files` نیامده، `.d.ts` شکسته، یا import بدون پسوند `.js` که در ESM واقعی کار نمی‌کند.

## تمرین

1. PostgreSQL را با `pgserver` بالا بیاورید و کل تست‌های پکیج را روی آن اجرا کنید.
2. یک تست E2E بنویسید که ثابت کند ویرایش پیام در زمان آفلاین بودن کاربر دیگر، بعد از اتصال مجدد به او می‌رسد (مسیر `updated_since`).
3. یک تست کامپوننت بنویسید که با یک `fakeFetch` خطای ۴۲۹ برگرداند و بررسی کند پیام `failed` می‌شود و دکمه‌ی Retry دارد.
