# فصل ۵ — امنیت

فایل‌های این فصل: `apps/server/accounts/api.py`، `accounts/authentication.py`، `ws/middleware.py`، `ws/tickets.py`، `files.py`، `api/views.py::_harden`، `apps/server/tests/test_hardening.py`، [security.md](../security.md)

## ۱. احراز هویت با session و CSRF

مرورگر بعد از ورود یک کوکی `sessionid` می‌گیرد که `HttpOnly` است (JavaScript نمی‌تواند بخواندش، پس XSS نمی‌تواند بدزددش). خطرش **CSRF** است: سایت مخرب فرمی به سرور شما می‌فرستد و مرورگر کوکی را خودکار ضمیمه می‌کند.

دفاع Django، الگوی **double-submit** است: یک کوکی `csrftoken` که JavaScript صفحه‌ی خودتان می‌تواند بخواند و در هدر `X-CSRFToken` برگرداند. سایت مخرب به کوکی شما دسترسی ندارد، پس نمی‌تواند هدر درست بسازد.

### تله: CSRF در ورود

DRF برای کاربر **احراز هویت نشده** CSRF را بررسی نمی‌کند. پس endpoint ورود بدون دفاع بود. حمله‌ی **login CSRF** یعنی مهاجم قربانی را بی‌صدا با حساب خود مهاجم وارد کند تا هر چه قربانی بعداً می‌نویسد در حساب مهاجم ثبت شود. راه‌حل در `accounts/api.py`:

```python
@method_decorator(csrf_protect, name="dispatch")
class LoginView(AuthView): ...
```

تست: `test_login_and_register_require_csrf`.

### تله: چرخش توکن CSRF

Django بعد از `login()` توکن CSRF را عوض می‌کند (جلوگیری از session fixation). کلاینتی که توکن قدیمی را نگه دارد، درخواست بعدی‌اش ۴۰۳ می‌گیرد. برای همین API ورود توکن جدید را در پاسخ برمی‌گرداند و `lib/auth.ts` آن را ذخیره می‌کند.

## ۲. WebSocket: origin و ticket

### Cross-Site WebSocket Hijacking

مرورگر روی handshake WebSocket هم کوکی می‌فرستد، **و برخلاف fetch، سیاست CORS را اعمال نمی‌کند.** هر سایتی می‌تواند `new WebSocket("wss://talkio.app/ws/chat/v1/")` باز کند و با کوکی قربانی پیام‌هایش را بخواند. تنها دفاع بررسی هدر `Origin` است. کد قدیمی این بررسی را نداشت. حالا `chat_websocket_application()` همیشه `AllowedHostsOriginValidator` را جلوی stack می‌گذارد و تست `test_session_auth_and_origin_validation` اتصال از `https://evil.example` را رد می‌کند.

### Ticket برای وقتی کوکی نمی‌رسد

اگر بک‌اند روی دامنه‌ی دیگری باشد یا میزبان از bearer token استفاده کند، socket کوکی ندارد. گذاشتن توکن اصلی در URL ایده‌ی بدی است (URLها log می‌شوند). راه‌حل (`ws/tickets.py`):

1. کلاینت با احراز هویت عادی HTTP درخواست `POST /ws-ticket/` می‌دهد.
2. سرور یک ticket امضاشده با `SECRET_KEY` می‌دهد که ۶۰ ثانیه اعتبار دارد.
3. ticket **فقط یک‌بار** قابل استفاده است: `cache.add(nonce)` اتمیک است و فقط اولین فراخوانی موفق می‌شود.

ticket لو رفته در log، بعد از یک دقیقه یا بعد از اولین استفاده بی‌ارزش است.

## ۳. Rate limiting و باگ `X-Forwarded-For`

سقف ۲۰ تلاش ورود در دقیقه برای هر IP، جلوی امتحان کردن رمزها (brute-force) را می‌گیرد. سؤال کلیدی: **IP کلاینت را از کجا می‌خوانیم؟**

- `REMOTE_ADDR`: آدرس واقعی اتصال TCP. قابل جعل نیست، ولی پشت reverse proxy آدرس خود proxy است و همه‌ی کاربران یک IP دارند.
- `X-Forwarded-For`: proxy آدرس واقعی کلاینت را اینجا می‌نویسد. ولی **هر کلاینتی می‌تواند این هدر را خودش بفرستد.**

DRF وقتی `NUM_PROXIES` تنظیم نشده باشد، کل `X-Forwarded-For` را قبول می‌کند. پس مهاجم با هر درخواست یک IP جعلی می‌فرستد و هیچ‌وقت محدود نمی‌شود. این باگ با یک تست ثابت شد: ۲۵ تلاش، صفر بار محدود. راه‌حل:

```python
"NUM_PROXIES": int(os.getenv("TRUSTED_PROXY_COUNT", "0")),
```

با `0` فقط `REMOTE_ADDR` خوانده می‌شود. با `1` (پشت یک proxy) فقط **آخرین** آدرس هدر خوانده می‌شود، یعنی همانی که proxy خودش اضافه کرده؛ آدرس‌های قبلی را کلاینت نوشته و بی‌اعتبارند.

**درس عمومی:** هر داده‌ای که از کلاینت می‌آید، از جمله هدرها، قابل جعل است مگر اینکه زنجیره‌ی اعتماد را دقیقاً تعریف کرده باشید.

## ۴. حریم خصوصی: ۴۰۴ به‌جای ۴۰۳

اگر کسی id یک گفتگوی خصوصی را حدس بزند و پاسخ ۴۰۳ (ممنوع) بگیرد، فهمیده که آن گفتگو وجود دارد. پس پروژه برای «وجود ندارد» و «عضو نیستی» هر دو ۴۰۴ برمی‌گرداند (`get_membership`). همین برای پیام‌ها و فایل‌ها هم اعمال می‌شود. idها هم UUID هستند، نه عدد پشت‌سرهم، تا تعدادشان قابل حدس نباشد.

## ۵. آپلود امن فایل

مرورگر `Content-Type` فایل را خودش اعلام می‌کند، و مهاجم می‌تواند `virus.exe` را با `image/png` بفرستد. کد قدیمی به همین اعلام اعتماد می‌کرد. لایه‌های دفاع در این پروژه:

1. **تشخیص از روی محتوا (magic bytes):** PNG همیشه با `89 50 4E 47 0D 0A 1A 0A` شروع می‌شود، JPEG با `FF D8 FF`، PDF با `%PDF-`. تابع `files.detect_content_type` نوع را از بایت‌ها تعیین می‌کند. نوع اعلام‌شده فقط در یک مورد استفاده می‌شود: انتخاب بین صوت و ویدئو برای containerهایی (WebM، MP4) که خودشان با اطمینان تشخیص داده شده‌اند.
2. **فهرست مجاز (allow-list)، نه فهرست ممنوع.** SVG هرگز مجاز نیست، چون می‌تواند `<script>` داشته باشد.
3. **بررسی واقعی تصویر با Pillow:** تصویر خراب یا **decompression bomb** (فایل کوچکی که به میلیاردها پیکسل باز می‌شود) رد می‌شود.
4. **نام تصادفی روی دیسک:** نام کاربر (`../../etc/passwd`) هرگز مسیر ذخیره نمی‌شود.
5. **storage خصوصی:** فایل‌ها در `MEDIA_ROOT` عمومی نیستند. در حالت DEBUG فقط `media/avatars/` سرو می‌شود؛ قبلاً همه‌ی `MEDIA_ROOT` سرو می‌شد و فایل‌های چت بدون احراز هویت قابل دانلود بودند.
6. **هدرهای پاسخ دانلود** (`_harden`): `nosniff` (مرورگر نوع را حدس نزند)، `Content-Security-Policy: default-src 'none'; sandbox` (حتی اگر HTML باز شود، اسکریپت اجرا نشود)، و `Content-Disposition: attachment` برای هر چیزی جز رسانه.

## ۶. XSS: رندر بی‌اثر

کد قدیمی پیام‌ها را با `innerHTML` درج می‌کرد، پس پیامی مثل `<img src=x onerror=alert(1)>` اجرا می‌شد. در React، متن به شکل **text node** رندر می‌شود و هرگز HTML تفسیر نمی‌شود. `MessageText` متن را با `tokenize` به تکه‌های متن و لینک تقسیم می‌کند و فقط `http(s)` لینک می‌شود (`javascript:` لینک نمی‌شود). لینک‌ها `rel="noopener noreferrer nofollow ugc"` دارند. تست `renders message text inertly` این را بررسی می‌کند.

یک حمله‌ی کمتر شناخته‌شده: **Trojan Source**. کاراکترهای کنترل جهت یونیکد (U+202E و مشابه) ترتیب نمایش متن را برعکس می‌کنند. `normalize_body` آن‌ها را حذف می‌کند.

## ۷. ورودی‌های بدشکل

کاربر می‌تواند به‌جای id عددی، `abc` یا `99999999999999999999999` بفرستد. اگر این مستقیم به کوئری برسد، `ValueError` یا `OverflowError` (و در Postgres خطای دیتابیس) می‌دهد که می‌شود خطای ۵۰۰. این امنیتی نیست، ولی هشدار مانیتورینگ و log می‌سازد و سطح حمله را بزرگ‌تر می‌کند. راه‌حل یک تابع مرکزی است: `users.clean_user_id` که نوع و بازه‌ی کلید اصلی را بررسی می‌کند. **اعتبارسنجی را در مرز سیستم و در یک جا انجام دهید.**

## ۸. ورود آزمایشی با کد ثابت

ورود با «هر شماره + ۱۲۳۴» عملاً یک **دور زدن احراز هویت** است. سه محافظ دارد:

1. فقط وقتی `DEBUG=1` فعال است (`DEMO_AUTH_ENABLED = env_bool(...) and DEBUG`)، و تستی هست که با `DEBUG=0` بررسی می‌کند همیشه خاموش است.
2. مقایسه با `secrets.compare_digest` (زمان ثابت، تا از زمان پاسخ نتوان کد را حدس زد).
3. username تصادفی، نه شماره‌ی تلفن (شماره‌ها به دیگران نشان داده نمی‌شوند).

## ۹. محدودیت‌های صادقانه

بخش «Known limitations» در [security.md](../security.md) را بخوانید: رمزنگاری end-to-end نیست، rate limit سوکت برای هر اتصال است، و غیره. **مستند کردن محدودیت‌ها بخشی از امنیت است**؛ ادعای امنیت بیش از واقعیت خطرناک‌تر از اعتراف به محدودیت است.

## تمرین

1. یک فایل HTML بسازید و پسوندش را `.png` بگذارید. آپلودش کنید. پاسخ سرور چیست و کدام خط کد آن را رد می‌کند؟
2. با `curl`، یک WebSocket handshake با `Origin: https://evil.example` و کوکی معتبر بزنید. چه کدی می‌گیرید؟
3. تست `test_login_throttle_cannot_be_bypassed_with_spoofed_forwarded_for` را بخوانید، موقتاً `NUM_PROXIES` را از تنظیمات حذف کنید و تست را اجرا کنید.
4. فکر کنید: اگر بخواهیم پیش‌نمایش لینک (عنوان و عکس سایت) اضافه کنیم، سرور باید URL را fetch کند. این چه خطر امنیتی‌ای دارد؟ (کلیدواژه: SSRF.)
