# Chapter 13 — Going bilingual: library, SDK and server

**English** · [فارسی](../13-i18n.md)

## The goal of this chapter

See how translating a **reusable library** differs from translating an **application**, why Talkio uses Django's standard gettext on the server but a plain dictionary in the web app, and which subtle bugs turned up along the way.

## Three layers, three owners

| Layer | Who writes the text | How it is translated |
| --- | --- | --- |
| Chat components (`@realtime-chat/react`) | the library, but the host project must be able to change it | typed `ChatStrings` + `faStrings` |
| The Talkio app (`apps/web`) | the app itself | `t('English text')` + `src/locales/fa.json` |
| Server messages (Django package and server) | the package and the app | Django gettext with `.po`/`.mo` |

The general rule: **whoever writes the text also provides the translation; but whoever uses it must be able to override it.**

## The library: strings are part of the API

From the start the library kept all its text in `strings.ts`, and `ChatProvider` let you override any subset (`strings={{ send: 'Go' }}`). For Persian, building one complete object was enough:

```ts
export const faStrings: ChatStrings = { conversations: 'گفت‌وگوها', send: 'ارسال', … };
```

The `ChatStrings` type is derived from `defaultStrings`; so if someone adds a new English key without its Persian counterpart, **the library build fails**. This is the same "automatic check" Dockra has, but this time with TypeScript's type system and no script.

A code review, however, revealed three "hidden" places that had escaped this system:

```ts
`${names[0]} & ${names[1]} ${strings.typingMany}`   // a fixed "&" and word order
`${names.length} people ${strings.typingMany}`        // an English "people"
aria-label={`${count} unread`}                        // for screen readers
```

All became new keys (`and`, `people`, `unread`). The lesson: "all the text is in one file" stays true only until someone glues a second sentence together with a template string.

## Intl does the hard work

`formatRelative` used to build "5 min ago" itself. Now:

```ts
const rtf = new Intl.RelativeTimeFormat(locale, { numeric: 'auto', style: 'short' });
rtf.format(-1, 'day');   // "yesterday" / «دیروز»
rtf.format(-5, 'minute'); // "5 min. ago" / «۵ دقیقه پیش»
```

The browser knows these phrases for hundreds of languages, with correct plurals and digits. Wherever you build "time ago" or a "number" yourself, first check whether `Intl` already has it. Member counts and the "unread" badge also got Persian digits through `Intl.NumberFormat`.

## The app: the language before the first render

Unlike the Dockra panel (Next.js), Talkio is a pure Vite SPA: the server does not render content into the HTML, so there is no hydration problem. A small script in `index.html` sets `<html lang dir>` from `localStorage` or the browser's language before React loads, and `lib/i18n.ts` reads the same value. The first render is Persian from the very start.

One subtlety: when the language changes, the app's text must re-render. The simplest way is remounting the whole tree with `key={lang}`, but then `ChatSession` is rebuilt too, the chat client is disposed and **the WebSocket disconnects and reconnects**. So the key sits **below** `ChatSession` (`<ByLang>` in `App.tsx`): the UI is rebuilt and the connection stays alive. The library components re-render on their own when `strings` changes in the context.

## The server: why gettext here?

In Dockra the API got a JSON dictionary. In Talkio the `django-realtime-chat` package's messages are translated with gettext. Why two different decisions?

- `django-realtime-chat` is a **pip package** installed in other projects. Django developers expect its translations to behave like Django's own: a project can override a text by putting the same msgid in its `LOCALE_PATHS`, and add other languages with familiar tools (Weblate, Poedit). Our personal taste should not win over the ecosystem's conventions.
- Dockra is an application nobody installs inside another project; simplicity mattered more there.

gettext's practical problem is that Django's `makemessages` and `compilemessages` need the GNU tools (`xgettext`, `msgfmt`), which are not on every machine. `scripts/i18n.py` does the same three jobs with only the Python standard library: `extract` finds `gettext()` calls with the `ast` module, `compile` writes the binary `.mo` file directly with `struct` (its format is a header of a few dozen bytes and two offset tables), and `check` makes sure in CI that no message is untranslated and no `.mo` is stale.

## Bug 1: a lazy string that would not become JSON

The errors' default messages are defined at class level. Calling `gettext()` there translates **at import time**, in the language of that moment, not the request's language. So `gettext_lazy` was used, which returns a "lazy" object that postpones translation until it is converted to a string.

The result: one of the WebSocket tests failed with `TypeError: Object of type __proxy__ is not JSON serializable`. The WebSocket consumer put `exc.message` straight into JSON, and `json` does not know what to do with a lazy object. The fix in `ChatError.__init__`:

```python
self.message = str(message or self.default_message)
```

That is, the message becomes a string **the moment the error is created**, in the language of the request that created it. The lesson: lazy translation is for module-level values; the boundary where data leaves the system (JSON, logs, queues) must see a real string.

## Bug 2: WebSockets do not pass through middleware

`LocaleMiddleware` sets the language of each HTTP request from `Accept-Language`. But in Channels a WebSocket connection does not go through Django's middleware, so socket errors were always in English. The consumer now determines the language itself (`connection_language` in `ws/consumer.py`):

1. the `?lang=` parameter in the socket URL (the SDK sends it from its `language` option),
2. otherwise the handshake request's `Accept-Language`,
3. otherwise `LANGUAGE_CODE`.

Every incoming event is processed inside `translation.override(self.language)`. Why `?lang=` when there is a header? Because browsers do not let you send custom headers on a WebSocket, and the browser's `Accept-Language` is the **browser's** language, not the language the user picked inside the app. For the same reason, the SDK sets `Accept-Language` itself on REST requests from its `language` option.

## Bug 3: the exclamation mark in the wrong place

The last-message preview in the conversation list was one string: `"شما: Thanks Farnaz, see you there!"` ("You: …" in Persian) with `dir="auto"`. The first strong character is Persian, so the whole line became right-to-left, and the bidirectional algorithm moved the "!" at the end of the English sentence to the other side: `!Thanks Farnaz, see you there :شما`.

The fix was separating the author label from the message text (`previewParts`): the label takes the page's direction and the message text goes inside `<bdi>`, an element that determines its direction from its own content, independently of its surroundings. Wherever user text (of unknown language) sits next to UI text (of known language), `<bdi>` is needed.
