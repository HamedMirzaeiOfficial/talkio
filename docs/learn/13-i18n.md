# فصل ۱۳ — دو زبانه کردن: کتابخانه، SDK و سرور

[English](en/13-i18n.md) · **فارسی**

## هدف این فصل

ببینید ترجمهٔ یک **کتابخانهٔ قابل استفادهٔ دوباره** با ترجمهٔ یک **اپلیکیشن** چه فرقی دارد، چرا Talkio در سرور gettext استاندارد جنگو را برداشت ولی در اپ وب یک دیکشنری ساده را، و چه باگ‌های ظریفی سر راه پیدا شد.

## سه لایه، سه صاحب

| لایه | چه کسی متن را می‌نویسد | راه ترجمه |
| --- | --- | --- |
| کامپوننت‌های چت (`@realtime-chat/react`) | کتابخانه، ولی پروژهٔ میزبان باید بتواند عوضش کند | `ChatStrings` تایپ‌شده + `faStrings` |
| اپ Talkio (`apps/web`) | خود اپ | `t('English text')` + `src/locales/fa.json` |
| پیام‌های سرور (پکیج Django و سرور) | پکیج و اپ | gettext جنگو با `.po`/`.mo` |

قاعدهٔ کلی: **کسی که متن را می‌نویسد، ترجمه را هم می‌دهد؛ ولی کسی که از آن استفاده می‌کند باید بتواند بازنویسی‌اش کند.**

## کتابخانه: رشته‌ها بخشی از API هستند

کتابخانه از اول همهٔ متن‌ها را در `strings.ts` داشت و `ChatProvider` اجازه می‌داد هر زیرمجموعه‌ای را عوض کنید (`strings={{ send: 'بفرست' }}`). برای فارسی کافی بود یک شیء کامل بسازیم:

```ts
export const faStrings: ChatStrings = { conversations: 'گفت‌وگوها', send: 'ارسال', … };
```

نوعِ `ChatStrings` از روی `defaultStrings` ساخته شده؛ پس اگر کسی کلید جدیدی به انگلیسی اضافه کند و فارسی‌اش را نه، **build کتابخانه می‌شکند**. این همان «بررسی خودکار» Dockra است، ولی این بار با سیستم نوع TypeScript و بدون اسکریپت.

ولی بررسی کد سه جای «پنهان» را نشان داد که از این سیستم بیرون مانده بودند:

```ts
`${names[0]} & ${names[1]} ${strings.typingMany}`   // «&» و ترتیب ثابت
`${names.length} people ${strings.typingMany}`        // «people» انگلیسی
aria-label={`${count} unread`}                        // برای صفحه‌خوان
```

همه به کلیدهای تازه (`and`، `people`، `unread`) تبدیل شدند. درس: «همهٔ متن‌ها در یک فایل‌اند» تا وقتی درست است که کسی جملهٔ دوم را با template string نچسبانده باشد.

## Intl کار سخت را می‌کند

`formatRelative` قبلاً خودش «5 min ago» می‌ساخت. حالا:

```ts
const rtf = new Intl.RelativeTimeFormat(locale, { numeric: 'auto', style: 'short' });
rtf.format(-1, 'day');   // "yesterday" / «دیروز»
rtf.format(-5, 'minute'); // "5 min. ago" / «۵ دقیقه پیش»
```

مرورگر برای صدها زبان این جمله‌ها را بلد است، با جمع و مفرد و ارقام درست. هر جا خودتان «زمان پیش» یا «عدد» می‌سازید، اول ببینید `Intl` آن را ندارد. شمار اعضا و نشان «نخوانده» هم با `Intl.NumberFormat` ارقام فارسی گرفتند.

## اپ: زبان قبل از اولین رندر

Talkio برخلاف پنل Dockra (Next.js) یک SPA خالص با Vite است: سرور HTML محتوادار نمی‌سازد، پس مشکل hydration نداریم. یک اسکریپت کوچک در `index.html` پیش از بارگذاری React `<html lang dir>` را از `localStorage` یا زبان مرورگر تنظیم می‌کند و `lib/i18n.ts` همان را می‌خواند. رندر اول از همان ابتدا فارسی است.

یک ظرافت: با عوض شدن زبان باید متن‌های اپ دوباره رندر شوند. ساده‌ترین راه remount کل درخت با `key={lang}` است، ولی آن وقت `ChatSession` هم از نو ساخته می‌شود، کلاینت چت dispose می‌شود و **WebSocket قطع و وصل می‌شود**. پس کلید را **زیر** `ChatSession` گذاشتیم (`<ByLang>` در `App.tsx`): رابط کاربری از نو ساخته می‌شود، اتصال زنده می‌ماند. کامپوننت‌های کتابخانه هم با عوض شدن `strings` در context خودشان دوباره رندر می‌شوند.

## سرور: چرا این‌جا gettext؟

در Dockra برای API یک دیکشنری JSON ساختیم. در Talkio پیام‌های پکیج `django-realtime-chat` با gettext ترجمه شدند. چرا دو تصمیم متفاوت؟

- `django-realtime-chat` یک **پکیج pip** است که در پروژه‌های دیگر نصب می‌شود. توسعه‌دهندهٔ Django انتظار دارد ترجمه‌ها مثل خود جنگو رفتار کنند: پروژه بتواند با گذاشتن همان msgid در `LOCALE_PATHS` متن را عوض کند، و زبان‌های دیگر را با ابزارهای آشنا (Weblate، Poedit) اضافه کند. سلیقهٔ شخصی ما نباید بر قرارداد اکوسیستم غلبه کند.
- Dockra یک اپلیکیشن است که کسی آن را داخل پروژهٔ دیگری نصب نمی‌کند؛ آن‌جا سادگی مهم‌تر بود.

مشکل عملی gettext این است که `makemessages` و `compilemessages` جنگو ابزارهای GNU (`xgettext`، `msgfmt`) را لازم دارند که روی هر ماشینی نیست. `scripts/i18n.py` همان سه کار را فقط با کتابخانهٔ استاندارد پایتون انجام می‌دهد: `extract` با ماژول `ast` فراخوانی‌های `gettext()` را پیدا می‌کند، `compile` فایل باینری `.mo` را مستقیم با `struct` می‌نویسد (قالبش چند ده بایت سربرگ و دو جدول offset است)، و `check` در CI مطمئن می‌شود هیچ پیامی بی‌ترجمه و هیچ `.mo`ی کهنه نیست.

## باگ ۱: رشتهٔ تنبل که JSON نمی‌شد

پیام پیش‌فرض خطاها در سطح کلاس تعریف شده‌اند. اگر آن‌جا `gettext()` صدا بزنیم، ترجمه **هنگام import** و با زبان آن لحظه انجام می‌شود، نه با زبان درخواست. پس از `gettext_lazy` استفاده کردیم که یک شیء «تنبل» برمی‌گرداند و ترجمه را تا لحظهٔ تبدیل به رشته عقب می‌اندازد.

نتیجه: یکی از تست‌های WebSocket با `TypeError: Object of type __proxy__ is not JSON serializable` شکست خورد. مصرف‌کنندهٔ WebSocket `exc.message` را مستقیم در JSON می‌گذاشت و `json` نمی‌داند با شیء تنبل چه کند. راه‌حل در `ChatError.__init__`:

```python
self.message = str(message or self.default_message)
```

یعنی پیام **همان لحظه‌ای که خطا ساخته می‌شود** به رشته تبدیل می‌شود، در زبانِ درخواستی که خطا را ساخته. درس: ترجمهٔ تنبل برای مقادیر سطح ماژول است؛ مرزی که داده از سیستم بیرون می‌رود (JSON، لاگ، صف) باید رشتهٔ واقعی ببیند.

## باگ ۲: WebSocket از middleware رد نمی‌شود

`LocaleMiddleware` زبان هر درخواست HTTP را از `Accept-Language` تنظیم می‌کند. ولی اتصال WebSocket در Channels از middlewareهای جنگو عبور نمی‌کند؛ پس خطاهای سوکت همیشه انگلیسی بودند. مصرف‌کننده حالا خودش زبان را تعیین می‌کند (`connection_language` در `ws/consumer.py`):

1. پارامتر `?lang=` در آدرس سوکت (SDK آن را از گزینهٔ `language` می‌فرستد)،
2. وگرنه `Accept-Language` درخواست handshake،
3. وگرنه `LANGUAGE_CODE`.

و هر رویداد دریافتی داخل `translation.override(self.language)` پردازش می‌شود. چرا `?lang=` وقتی هدر هست؟ چون مرورگر اجازه نمی‌دهد برای WebSocket هدر دلخواه بفرستید و `Accept-Language` مرورگر زبان **مرورگر** است، نه زبانی که کاربر داخل اپ انتخاب کرده. به همین دلیل SDK برای درخواست‌های REST هم `Accept-Language` را خودش از گزینهٔ `language` می‌گذارد.

## باگ ۳: علامت تعجب در جای اشتباه

پیش‌نمایش آخرین پیام در فهرست گفت‌وگوها یک رشته بود: `«شما: Thanks Farnaz, see you there!»` با `dir="auto"`. اولین حرف قوی فارسی است، پس کل خط راست‌به‌چپ شد و الگوریتم دوجهته «!» انتهای جملهٔ انگلیسی را به سمت دیگر برد: `!Thanks Farnaz, see you there :شما`.

راه‌حل این بود که برچسب نویسنده و متن پیام از هم جدا شوند (`previewParts`): برچسب جهت صفحه را می‌گیرد و متن پیام داخل `<bdi>` می‌رود؛ عنصری که جهتش را مستقل از اطرافش از محتوای خودش تعیین می‌کند. هر جا متن کاربر (با زبان نامعلوم) کنار متن رابط (با زبان معلوم) می‌نشیند، `<bdi>` لازم است.

## تمرین

1. یک کلید جدید به `defaultStrings` اضافه کنید و `npm run build:packages` را اجرا کنید. خطا کجاست؟ چرا این بهتر از یک اسکریپت بررسی است؟
2. در پروژهٔ مثال `examples/django-integration` یک فایل `locale/fa/LC_MESSAGES/django.po` بسازید که ترجمهٔ «Message not found.» را عوض کند. کدام ترجمه برنده می‌شود و چرا؟ (راهنما: ترتیب جست‌وجوی جنگو.)
3. تست `test_default_message_follows_the_active_language` را بخوانید. چرا دو ترجمهٔ ممکن را می‌پذیرد؟
4. خط `self.message = str(...)` را برگردانید و تست‌های WebSocket را اجرا کنید. خطا را با «باگ ۱» مقایسه کنید.
5. با devtools مرورگر آدرس اتصال WebSocket را ببینید. `lang` را عوض کنید (از تنظیمات) و دوباره نگاه کنید. چرا آدرس فقط بعد از اتصال دوباره عوض می‌شود؟
