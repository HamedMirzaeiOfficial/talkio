# فصل ۶ — SDK تایپ‌اسکریپت: شبکه‌ی ناپایدار، state پایدار

[English](en/06-typescript-sdk.md) · **فارسی**

فایل‌های این فصل: `packages/chat-client/src/{http,socket,store,client,auth,errors}.ts` و تست‌ها در `packages/chat-client/test/`

## ۱. چرا SDK مستقل از React؟

منطق سخت چت (پیام‌های optimistic، بازیابی بعد از قطعی، شمارش خوانده‌نشده) هیچ ربطی به React ندارد. اگر در کامپوننت‌ها نوشته شود، برای Vue یا اپ موبایل باید دوباره نوشته شود، و تست کردنش هم به DOM نیاز دارد. پس SDK یک **store** با دو متد ساده می‌دهد: `subscribe(listener)` و `getState()`. هر فریم‌ورکی می‌تواند به آن وصل شود ([ADR 0005](../architecture/decisions/0005-store-in-the-sdk.md)).

## ۲. خطاهای یکسان: `ChatError`

هر شکستی (HTTP 400، قطع شبکه، timeout، لغو) یک `ChatError` با `kind` مشخص است. مزیتش این است که UI فقط یک نوع خطا را مدیریت می‌کند و می‌تواند بپرسد `error.retryable` (آیا تلاش دوباره منطقی است؟) یا `error.retryAfter` (چند ثانیه صبر کنم؟).

## ۳. احراز هویت بدون ذخیره‌ی توکن

```ts
bearerAuth({ getToken: () => auth.currentAccessToken() })
```

SDK توکن را **نگه نمی‌دارد**. برای هر درخواست از میزبان می‌پرسد. پس:

- refresh توکن کار میزبان است و SDK خودکار نسخه‌ی جدید را می‌گیرد.
- SDK هیچ‌وقت توکن را در `localStorage` نمی‌گذارد (جایی که XSS می‌تواند بخواندش).

تست `adds auth headers per request and never caches the token` همین را بررسی می‌کند.

## ۴. لغو درخواست و timeout

`HttpClient.request` دو `AbortSignal` را ترکیب می‌کند: سیگنال فراخواننده (مثلاً وقتی کاربر جستجو را تایپ می‌کند و درخواست قبلی بی‌فایده می‌شود) و یک timeout داخلی. مهم است این دو را از هم تشخیص دهیم: لغو توسط کاربر خطا نیست (`kind: aborted` گزارش نمی‌شود)، ولی timeout خطاست.

## ۵. WebSocket به‌عنوان state machine

اتصال یک `boolean` نیست؛ حالت‌های مختلفی دارد که UI باید متفاوت نشانشان دهد (شکل در [frontend.md](../frontend.md#13-socket-socketts)). مدل کردن صریح حالت‌ها (`idle`، `connecting`، `open`، `reconnecting`، `offline`، `unauthenticated`، `closed`) جلوی باگ‌هایی مثل «دو اتصال همزمان» را می‌گیرد. یک شمارنده‌ی `generation` هم هست: اگر در حین باز شدن اتصال `disconnect()` صدا زده شود، باز شدن قبلی بی‌اثر می‌شود.

### Backoff نمایی با full jitter

اگر سرور restart شود و ۱۰ هزار کلاینت دقیقاً بعد از ۱ ثانیه وصل شوند، سرور دوباره از کار می‌افتد (**thundering herd**). راه‌حل:

```
ceiling = min(max, min × 2^(attempt-1))     // 0.5s, 1s, 2s, 4s ... تا 30s
delay   = random() × ceiling                 // پخش تصادفی در کل بازه
```

به این «full jitter» می‌گویند و از رایج‌ترین الگوهای مهندسی سیستم‌های توزیع‌شده است. تست با `random: () => 1` آن را قطعی می‌کند.

### Heartbeat: تشخیص اتصال مرده

اگر Wi-Fi قطع شود، TCP ممکن است دقیقه‌ها «باز» بماند، چون هیچ بسته‌ی close نرسیده (**half-open connection**). پس کلاینت هر ۳۰ ثانیه `ping` می‌فرستد و اگر ظرف ۱۰ ثانیه `pong` نیاید، خودش اتصال را می‌بندد و دوباره وصل می‌شود. همین ping در سرور lease حضور را هم تمدید می‌کند. یک مکانیزم، دو کاربرد.

### رویداد `offline` مرورگر

در یک تست E2E معلوم شد Chromium وقتی آفلاین می‌شود، WebSocket باز را نمی‌بندد. پس SDK روی رویداد `offline` خودش socket را می‌بندد تا UI بلافاصله «آفلاین» نشان دهد، و با `online` فوراً (بدون صبر برای backoff) وصل می‌شود.

## ۶. Store تغییرناپذیر (immutable)

هر تغییر یک شیء state جدید می‌سازد و قسمت‌های تغییرنکرده را **همان ارجاع قبلی** نگه می‌دارد (structural sharing):

```ts
return { ...s, conversations: { ...s.conversations, [id]: updated } };
```

چرا؟ React (و هر UI دیگری) برای فهمیدن «تغییر کرد؟» کافی است ارجاع‌ها را مقایسه کند (`===`)، نه کل شیء را. کامپوننتی که فقط به گفتگوی A گوش می‌دهد، با تغییر گفتگوی B re-render نمی‌شود.

## ۷. Optimistic UI و تطبیق (reconciliation)

کاربر انتظار دارد پیامش **فوراً** ظاهر شود، نه بعد از رفت‌وبرگشت شبکه. پس SDK یک پیام محلی با وضعیت `pending` و `seq = Number.MAX_SAFE_INTEGER` (یعنی همیشه آخر لیست) می‌سازد. وقتی نسخه‌ی سرور می‌رسد، `mergeMessages` نسخه‌ی محلی را با `client_id` پیدا و جایگزین می‌کند.

ظرافت مهم: نسخه‌ی سرور از **دو مسیر** می‌رسد: `ack` به فرستنده، و broadcast `message.created` به همه، از جمله فرستنده. ترتیب رسیدن‌شان تضمینی نیست. `mergeMessages` طوری نوشته شده که ترتیب مهم نباشد (عملیات **idempotent** در سمت کلاینت). تست `the broadcast can arrive before the ack` همین را پوشش می‌دهد.

### fallback از WebSocket به HTTP

```
اگر socket باز است → message.send و صبر برای ack (۸ ثانیه)
اگر ack نیامد یا اتصال قطع شد → POST همان پیام با همان client_id
```

چون سرور idempotent است، اگر پیام اول در واقع رسیده بود، POST همان را برمی‌گرداند و تکراری نمی‌شود. این نقطه‌ای است که طراحی فصل ۳ (idempotency) و فصل ۶ (fallback) به هم وصل می‌شوند.

اگر خطا از جنس اعتبارسنجی باشد (مثلاً پیام بیش از حد طولانی)، fallback انجام نمی‌شود و پیام `failed` می‌شود، چون تکرار فایده‌ای ندارد.

## ۸. بازیابی بعد از قطع اتصال

وقتی socket دوباره وصل می‌شود (`ready.recovered === true`):

1. لیست گفتگوها دوباره بارگذاری می‌شود (شمارنده‌ی خوانده‌نشده، گفتگوهای جدید).
2. برای هر گفتگوی باز: `GET messages?after=<آخرین seq>` (پیام‌های جاافتاده).
3. `GET messages?updated_since=<زمان اتصال قبلی>` (ویرایش‌ها، حذف‌ها و ری‌اکشن‌هایی که در زمان قطعی رخ داده).
4. پیام‌هایی که به خاطر قطع شبکه شکست خورده بودند، با همان `client_id` دوباره فرستاده می‌شوند.

جدا از این، **تشخیص فاصله** در حین اتصال هم هست: اگر `message.created` با `seq = 10` برسد در حالی که آخرین پیام دیده‌شده ۷ بوده، `fetchGap` پیام‌های ۸ و ۹ را می‌گیرد.

تست E2E `goes offline, shows the banner, then recovers and catches up` کل این مسیر را با دو مرورگر واقعی اجرا می‌کند.

## ۹. Debounce و throttle

- `markRead`: debounce ۲۵۰ میلی‌ثانیه. اگر ۲۰ پیام پشت‌سرهم برسد، فقط یک درخواست زده می‌شود.
- `setTyping`: throttle؛ حداکثر یک `typing.start` در هر ۳ ثانیه.

تفاوت: **debounce** یعنی «صبر کن تا رویدادها تمام شوند، بعد یک‌بار اجرا کن». **throttle** یعنی «حداکثر هر X ثانیه یک‌بار اجرا کن».

## ۱۰. Dispose: پاک‌سازی کامل

SDK در طول کار تایمر، listener، blob URL و socket می‌سازد. `dispose()` همه را آزاد می‌کند. یک باگ کوچک اینجا پیدا شد: پرچم `disposed` در انتهای تابع ست می‌شد، پس بستن socket در حین dispose یک به‌روزرسانی آخر به store می‌فرستاد. **پرچم «تمام شد» را اول ست کنید.**

## تمرین

1. تست `reconnects with exponential backoff` را بخوانید و توضیح دهید چرا از `vi.useFakeTimers()` استفاده شده.
2. در `client.ts` تابع `deliver` را دنبال کنید و همه‌ی مسیرهایی را که به `status: 'failed'` ختم می‌شوند فهرست کنید.
3. یک adapter جدید `cookieTicketAuth` بنویسید که از session استفاده کند ولی برای WebSocket ticket بگیرد (برای بک‌اند روی دامنه‌ی دیگر). چه فیلدهایی از `AuthAdapter` لازم است؟
